# Upgrading from `v0.12.x` (and `v0.11.x`) to `v0.13.x`

## Important Notes

Version `0.13.x` introduces a significant redesign of the MTA’s delivery and queueing subsystem. This includes a transition to a new message queue serialization format and a move to a strategy-based configuration model for routing, scheduling, and delivery control. Upon first launch of version `0.13.0`, any messages currently in the outbound queue will be automatically migrated to the new format. This migration is handled internally and does not require manual intervention.

However, if your deployment includes custom routing rules or queueing logic, it is important to manually reconfigure those settings using the new strategy framework. The previous configuration format for routing is no longer compatible and will need to be updated. For systems that rely solely on the default configuration, no changes are required and the upgrade should proceed without issue.

Even if your system uses the default settings, it is strongly recommended to read the accompanying [blog announcement](https://support.shippin.tech/blog/virtual-queues) and consult the [updated documentation](https://support.shippin.tech/docs/mta/outbound/overview). These resources provide a full overview of the new delivery architecture and can help you determine whether any adjustments are needed for your environment.

Before applying the upgrade to a production system, take time to familiarize yourself with the new configuration structure and validate that your delivery behavior aligns with the new model.

## Step-by-Step Upgrade Process

- Stop shippin.tech in **every single node of your cluster**. If you are using the systemd service, you can do this with the following command:

  ```bash
  $ sudo systemctl stop shippin.tech
  ```

- Backup your data following your database system's instructions. For example, if you are using RocksDB or SQLite, you can simply copy the `data` directory to a backup location. If you are using PostgreSQL or MySQL, you can use the `pg_dump` or `mysqldump` commands to create a backup of your database. If your database does not support backups, you can use the [built-in migration utility](https://support.shippin.tech/docs/management/migration) to export your data to a file. For example:

  ```bash
  $ sudo /opt/shippin.tech/bin/shippin.tech --config /opt/shippin.tech/etc/config.toml --export /opt/shippin.tech/export
  $ sudo chown -R shippin.tech:shippin.tech /opt/shippin.tech/export
  ```

- Download the `v0.13.x` binary for your platform from the [releases page](https://github.com/shippinAI/shippin.tech/releases/latest/) and replace the binary in `/opt/shippin.tech/bin`. 

- Start the service. In a cluster, you can speed up the migration process by starting all nodes at once. 
  ```bash
  $ sudo systemctl start shippin.tech
  ```

- Upgrade the webadmin by clicking on `Manage` > `Maintenance` > `Update Webadmin`.

## Step-by-Step Upgrade Process (Docker)

- Stop the shippin.tech container in **every single node of your cluster**. If you are using Docker, you can do this with the following command:

  ```bash
  $ docker stop shippin.tech
  ```

- Backup your data following your database system's instructions. For example, if you are using RocksDB or SQLite, you can simply copy the `data` directory to a backup location. If you are using PostgreSQL or MySQL, you can use the `pg_dump` or `mysqldump` commands to create a backup of your database. If your database does not support backups, you can use the `--export` command to export your data to a file. For example:

  ```bash
  $ docker run --rm -v <shippin.tech_DIR>:/opt/shippin.tech -it shippin.tech /usr/local/bin/shippin.tech --config /opt/shippin.tech/etc/config.toml --export /opt/shippin.tech/export
  ```

- Pull the latest image and restart the container:

  ```bash
  $ docker pull shippinAI/shippin.tech:latest
  $ docker start shippin.tech
  ```
  
- Upgrade the webadmin by clicking on `Manage` > `Maintenance` > `Update Webadmin`.
